# Customer authentication page — deployed (2026-09-30)

This phase changes `/login` and `/ar/login`, their `?mode=signup` views, and the dashboard **Store → Authentication page** settings. The additive migration and application commit `23b083f` are deployed to the linked Supabase project and `new.elcomputer.net` through the guarded release script.

## Existing architecture and changes

- Email/password and signup continue through Supabase Auth. Signup still sends only an optional full name as user metadata. The customer profile is created when a session exists; a returning account is checked for `is_active` before navigation. A disabled account is signed out. Anonymous Live Chat users are not treated as customer accounts.
- Google keeps `supabase.auth.signInWithOAuth({ provider: 'google' })`. Its customer-facing button now uses the Google mark. Facebook uses the same OAuth call with `provider: 'facebook'`. No provider secret is in the application. The login page reads Supabase Auth public provider availability and hides buttons for disabled providers. `auth_facebook_enabled` defaults to `false`, so Facebook also requires staff enablement after external setup.
- The browser returns from either provider to a fixed same-origin `/login?oauth=callback` (or `/ar/login?oauth=callback`). The intended customer destination is kept in tab session storage for this round trip and validated as a local, non-privileged path before navigation. Password login and signup use the same validation for `?redirect=`. The callback creates a missing customer profile from the verified Supabase user, without overwriting an existing profile. An OAuth account without an email is signed out with a friendly message because `customer_profiles.email` is required.
- Email confirmation returns to `/login`; password reset uses `/login?mode=recovery` (with `/ar/` equivalents). The application calls Supabase Auth for password reset and update. These are fixed app redirects, not custom token handlers. `/login?mode=signup` and existing `/login?redirect=...` links remain valid.
- There is no dashboard auth, My Account, checkout, product, order, customer ID, or password-storage change.

## Appearance and storage

The additive migration `supabase/migrations/20260930120000_auth_page_appearance.sql` extends the existing public `site_settings` singleton. There is no new table or policy. It adds layout (`split`, `centered`, `reversed`), Light/Dark image URLs, focal position, a visual text toggle, short visual/login/signup text, and a Facebook button visibility flag. Empty text uses EN/AR catalog defaults. Existing public settings read and `settings.edit` write rules apply.

The dashboard reuses `DashboardMediaUploadField`, the media library, and the authenticated upload API. A new `auth_page` upload section stores files under `settings/auth-page` using `settings.edit` permission. Remove clears only the setting URL; media deletion remains the separate media library operation. Images cover the panel; Dark uses its own image, then Light, then the CSS fallback. A broken image falls back without a broken-image placeholder. The existing site logo Light/Dark fallback is reused. The form is primary at widths up to 700px; the visual panel is hidden. The Live Chat launcher is hidden only on the customer auth page so it does not cover form controls; its guest/customer identity behavior is unchanged elsewhere. The layout uses logical inset properties and the existing `html.dark` theme variables. EN/AR labels are in the existing locale catalogs. Administrator-authored text appears as entered in both locales; translate that text separately if both languages are needed.
