# Customer authentication page — local implementation (2026-09-30)

This phase changes `/login` and `/ar/login`, their `?mode=signup` views, and the dashboard **Store → Authentication page** settings. It does not deploy the application or apply the database migration.

## Existing architecture and changes

- Email/password and signup continue through Supabase Auth. Signup still sends only an optional full name as user metadata. The customer profile is created when a session exists; a returning account is checked for `is_active` before navigation. A disabled account is signed out. Anonymous Live Chat users are not treated as customer accounts.
- Google keeps `supabase.auth.signInWithOAuth({ provider: 'google' })`. Its customer-facing button now uses the Google mark. Facebook uses the same OAuth call with `provider: 'facebook'`. No provider secret is in the application. `auth_facebook_enabled` defaults to `false`, so the button is hidden until staff deliberately enables it after external setup.
- The browser returns from either provider to a fixed same-origin `/login?oauth=callback` (or `/ar/login?oauth=callback`). The intended customer destination is kept in tab session storage for this round trip and validated as a local, non-privileged path before navigation. Password login and signup use the same validation for `?redirect=`. The callback creates a missing customer profile from the verified Supabase user, without overwriting an existing profile. An OAuth account without an email is signed out with a friendly message because `customer_profiles.email` is required.
- Email confirmation returns to `/login`; password reset uses `/login?mode=recovery` (with `/ar/` equivalents). The application calls Supabase Auth for password reset and update. These are fixed app redirects, not custom token handlers. `/login?mode=signup` and existing `/login?redirect=...` links remain valid.
- There is no dashboard auth, My Account, checkout, product, order, customer ID, or password-storage change.

## Appearance and storage

The additive migration `supabase/migrations/20260930120000_auth_page_appearance.sql` extends the existing public `site_settings` singleton. There is no new table or policy. It adds layout (`split`, `centered`, `reversed`), Light/Dark image URLs, focal position, a visual text toggle, short visual/login/signup text, and a Facebook button visibility flag. Empty text uses EN/AR catalog defaults. Existing public settings read and `settings.edit` write rules apply.

The dashboard reuses `DashboardMediaUploadField`, the media library, and the authenticated upload API. A new `auth_page` upload section stores files under `settings/auth-page` using `settings.edit` permission. Remove clears only the setting URL; media deletion remains the separate media library operation. Images cover the panel; Dark uses its own image, then Light, then the CSS fallback. A broken image falls back without a broken-image placeholder. The existing site logo Light/Dark fallback is reused. The form is primary at widths up to 700px; the visual panel is hidden. The Live Chat launcher is hidden only on the customer auth page so it does not cover form controls; its guest/customer identity behavior is unchanged elsewhere. The layout uses logical inset properties and the existing `html.dark` theme variables. EN/AR labels are in the existing locale catalogs. Administrator-authored text appears as entered in both locales; translate that text separately if both languages are needed.

## External configuration before release

1. Apply the additive migration in the intended Supabase environment through the normal migration process. Until then the login page uses defaults and the new dashboard save cannot persist.
2. In **Supabase Dashboard → Authentication → URL Configuration**, inspect the current Site URL. Project notes last observed `http://localhost:3000`; this was not rechecked or changed during this phase. Set the production Site URL to the actual production app origin when authorized. Add the fixed production Redirect URLs used by the application: `https://new.elcomputer.net/login`, `https://new.elcomputer.net/login?oauth=callback`, `https://new.elcomputer.net/login?mode=recovery`, and the same three paths under `https://new.elcomputer.net/ar/login`. Add exact local equivalents for the development origin if local email/OAuth testing is needed. Supabase can otherwise fall back to an old Site URL for email flows. Confirm the URL list in the dashboard before relying on confirmations or resets. See [Supabase redirect URL guidance](https://supabase.com/docs/guides/auth/redirect-urls).
3. For Google, retain the existing provider and credentials in Supabase. Confirm the Google authorized redirect URI equals the **Supabase provider callback URL**, and that the production app origin is in Google's authorized JavaScript origins. The application callback URL above belongs in Supabase's Redirect URLs. See [Supabase Google setup](https://supabase.com/docs/guides/auth/social-login/auth-google).
4. For Facebook, create a Meta app with Facebook Login. In Meta **Facebook Login → Settings**, set Valid OAuth Redirect URIs to the exact Supabase provider callback shown in **Supabase Dashboard → Authentication → Providers → Facebook** (normally `https://zsqhuwgoasrexdnamlks.supabase.co/auth/v1/callback` for this project). Configure the `email` permission and app availability for intended customers. Enter the Meta App ID and App Secret in Supabase's Facebook provider settings, enable the provider, then test with an authorized Meta test user. Only after that should staff enable **Show Facebook sign in** in the store dashboard. The Meta secret stays in Supabase. See [Supabase Facebook setup](https://supabase.com/docs/guides/auth/social-login/auth-facebook).

## Verification and remaining acceptance

The local gates passed: **174 repository tests**, Nuxt typecheck, production build and `git diff --check`. The new redirect tests cover local destinations, external URLs and privileged routes. A PGlite migration check confirmed defaults and layout constraints; the read-only linked migration list showed `20260930120000` pending. Local Chrome checked seven anonymous login/signup screens at 1440, 768 and 390px across EN/AR and Light/Dark. These had no horizontal overflow, page exceptions or console errors. A browser interaction confirmed the password visibility control updates its type, pressed state and label; labels and autocomplete attributes were present. The local uploaded logo path serves a deliberately blank fixture, so screenshots do not verify production logo appearance.

A real valid/invalid password login, signup confirmation/duplicate email, disabled account, Google consent, Facebook consent, password reset email, authenticated profile write, and dashboard upload/save require a configured test identity and the migrated remote environment. They are not established by static tests or anonymous browser rendering. Manually inspect `/login`, `/login?mode=signup`, `/login?mode=forgot`, and `/login?mode=recovery` in EN/AR, Light/Dark, and desktop/tablet/mobile widths, including keyboard focus and long error messages. Verify the browser console and server output during authenticated acceptance.
