# Checkout identity and recovery

H3 requires application code with migration82, `20261015000000_checkout_commands.sql`. It preserves the existing normal/preorder order creators, pricing, inventory, ERP, coupon, payment-status, warranty and SMS transactions. The corrected API never acknowledges an order from a cart-ID lookup alone.

## Review and command

Authenticated `POST /api/checkout/quote` now receives the cart ID, products/variants/quantities, address, delivery, payment method, coupon and locale. The server validates and normalizes that content using the verified customer identity. A service-only database routine aggregates/sorts lines and computes its own canonical intent hash. Prices, discounts, fees and preorder deposit terms come from locked database records. Quotes have random IDs and expire after five minutes. The private quote records retain IDs, hashes, expiration and a reset flag; they contain no address, item list, price or token.

The response supplies the actual line titles/options/quantities, subtotal, discount, fee, total and required payment. Quotes reserve no stock and record no payment. Physical availability, cached ERP stock and publication are checked; the established order creators still enforce allocation, warehouse balances, coupon limits, preorder caps and reservations at commit. Shipping retains its existing single `shipping` choice and cost calculated later. Gateways remain configuration-gated.

`POST /api/checkout` supplies the same normalized intent and a quote ID. The database takes the shared System Reset exclusion, verifies and SHARE-locks the active customer profile, and serializes the cart command UUID across accounts. It validates the quote's customer/cart/content/expiration and recomputes trusted financial terms under locks. Changed prices, fees, publication, coupon eligibility or other reviewed terms require another review. The established creator and receipt insert commit in one transaction. Any failure rolls back orders, allocation, coupon consumption and transactional side effects.

The command receipt binds the customer, canonical content and original quote ID to one order. Identical retries return that order before checking today's quote expiration, stock, price or coupon limits. They create no second order, reservation, coupon use or financial posting. Changed products, variants, quantities, names, email, phone, delivery address, delivery/payment method, coupon, language or quote ID produce an explicit conflict. Client fingerprints and financial values have no authority. Another account cannot reuse a committed command UUID. Authorization runs on every replay.

Both receipt tables have RLS, no browser/service table grants, no erasure-blocking foreign keys and explicit reset coverage. Only service-role callers can execute the new RPCs. All old normal/preorder/external checkout entry points lose browser/service execution grants; their transaction routines remain callable inside the definer. No existing staff inventory or accounting grant is broadened.

Migration82 captures existing orders with cart IDs as **denial receipts** with unknown content hashes. It does not claim to reconstruct historical intent. Those commands require My Account reconciliation; they never silently confirm or overwrite a historical order.

## Browser behavior

The cart uses one versioned localStorage envelope with an ID, revision, items and coupon. Existing browser carts are migrated when first read. Storage events, focus and visibility refresh other tabs; mutations also read the latest envelope before writing. Cart changes invalidate the review and return checkout to delivery review. Payment changes refresh the summary and disable confirmation while the quote is unavailable. Back/Forward and reload restore the current cart. Cached clients without the new quote contract fail closed and need a refresh.

Before sending, checkout stores the exact request, original cart revision and reviewed summary in account-scoped localStorage. Web Locks coordinate tabs where supported; database locks remain the final authority. An uncertain acknowledgement keeps that command through navigation/reload/tab closure. An explicit **Recover checkout** control shows the original items/options/quantities, address, payment and total, and retries the original request without obtaining a replacement quote. The ordinary confirmation control stays disabled while recovery is pending.

Successful recovery records an immutable consumed-revision marker without rewriting the mutable cart envelope. Tabs hide that exact consumed revision; a newer revision stays intact and resolves to a shared fresh ID. This also prevents a cart edit interleaved with acknowledgement from being erased. The next ordinary cart mutation persists the resolved ID. Existing confirmations remain accessible through My Account. Definite quote/content/reset conflicts require explicit cart review; the browser does not automatically submit a new purchase. Storage failure blocks a new checkout before any request. Clearing browser storage, switching devices or losing the command requires order-history review before deliberately ordering again; no cross-device command recovery is claimed. Local pending requests contain delivery information, scoped to the account using that browser, until resolved.

## Reset compatibility

Products, Orders, Commerce, Store Content and Full retire quotes. Orders, Commerce and Full also retire command receipts before business erasure. Documents, Media and Analytics preserve their authority. All scopes retain minimal receipt rows; existing salary, catalog, installation and reset receipts keep their original policies. An exact acknowledgement can still recover an order retained by Products or Store Content reset. Erased orders cannot be recreated with retired commands, even if their former product IDs reappear. Full also invalidates deleted customer accounts; the owner survives and new customer/cart/order flows work after ordinary reinitialization.

This is a composed disposable native-schema correction, not installer recertification. Migrations1–81, release-79-v1 certificates and production infrastructure remain unchanged. Guided82, hosted services, real providers and deployment require separate authorization. Final native, compiled-browser, regression and reset evidence is recorded in the H3 acceptance report.
