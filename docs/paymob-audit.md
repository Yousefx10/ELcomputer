# Paymob foundation audit — 2026-10-04

Audit completed before implementation. Local working tree was clean. AGENTS.md, current PROJECT_STATE.md/CODEX_HANDOFF.md payment/preorder/ERP notes, deployment/environment conventions, checkout/quote/account/admin APIs, payment settings UI, migrations/schema/RLS, and existing PGlite tests were inspected. Searches covered card, payment(s), payment_method, checkout, PayPal, InstaPay, bank transfer, cash, transaction, gateway, provider, webhook, callback, refund, order/payment status.

- `POST /api/checkout` authenticates with `requireCustomerRequest`; orders belong to the verified active customer. Existing `commerce_create_customer_order` wraps the legacy transactional RPC with selling-mode guards. It locks products/inventory, uses the cart UUID uniqueness/advisory lock and calculates catalog prices/coupon totals. Insert trigger adds configured payment fee. Shipping is calculated later, outside this payable snapshot.
- Normal order/payment states are separate. Orders start `pending_payment`; payments support pending/partially_paid/paid/failed/refunded. Preorders have their own amount-paid ledger; this task excludes that lifecycle.
- `site_settings` and existing dashboard payment section control card/cash/manual bank transfer/InstaPay/PayPal labels, availability and fees. Cash is the schema default. Card/PayPal are unconnected presentation; card currently owns raw fields and fictitious saved previews. Transfer receipt selection is not secure submission. Staff must verify funds; no automated manual-payment confirmation is implemented.
- Treasury transactions reference built-in sales/procurement/employees, not customer gateway attempts. `preorder_payments` represents staff-verified preorder receipts only. Shipping webhook events are shipping-specific. None safely represent a normal-order intention, integration/mode binding and several provider transactions. A small private gateway-attempt/transaction ledger is necessary.
- Orders have existing customer read RLS; browser checkout RPC execution is revoked. New ledgers must have RLS with no browser grants/policies and only service-role RPC execution. Frontend reads safe projections through authenticated owner APIs.
- Stock/serialized allocation occurs once in the existing order transaction. Gateway callbacks must not recreate orders, change inventory, or repeat fulfillment. Shipping already requires paid state. Packing normally allows pending-payment orders (cash); unpaid gateway orders need a narrowly scoped guard.
- Secrets use private Nuxt runtime configuration and PM2 `NUXT_*` overrides. Production builds omit local dotenv. No secret settings table or new dashboard subsystem is needed; reuse `payment_card_enabled` and fee, with independent environment gateway gate.
- Current official Paymob documentation read: Create Intention (updated June 1, 2026), Pixel Embedded (September 7, 2026), Transaction callbacks and HMAC Transaction Callback (June 1, 2026). Egypt uses `https://accept.paymob.com/v1/intention/`, Token secret-key authorization, integer cents, public key/client secret for Pixel. HMAC signs the documented 20 values; browser return is presentation only.
- Merchant-provided configuration: TEST VPC/online/EGP integration 5899155. Keep this value in operator configuration only. Old `https://elcomputer.net?wc-api=paymob_callback` URLs belong to WooCommerce and must be replaced manually after review/deployment.

Sources: [Intention](https://developers.paymob.com/paymob-docs/developers/intention-apis/create-intention), [Pixel](https://developers.paymob.com/paymob-docs/developers/checkout-experiences/pixel-embedded), [callbacks](https://developers.paymob.com/paymob-docs/developers/transaction-callbacks), [HMAC field order](https://developers.paymob.com/paymob-docs/developers/webhook-callbacks-and-hmac/hmac/hmac-transaction-callback).
