## Security and architecture review — 2026-10-04

**Verdict: SAFE TO PROCEED TO STAGING REVIEW.** This approves the foundation for further review, not activation, a production release, or payment certification. Review baseline: committed foundation `a325cf0` against `90837e3`. No Critical or High defect was found. Five genuine defects were corrected:

| Severity | Finding | Exact correction |
| --- | --- | --- |
| Medium | Raw `CARD` / ` card ` skipped the availability gate, then normalized to Card and could create an order/allocate stock while Paymob was disabled. | Normalize the method before checking gateway configuration. Existing cart retries still return their original order. |
| Medium | Webhook size was checked after the entire public request had been buffered. | Read at most 65,536 bytes while receiving; reject oversized Content-Length immediately, reject overflowing chunked bodies before upload completion, and close stalled uploads after 10 seconds. Parsing/signature/state processing happen afterward. |
| Medium | Unrelated edits to historical unpaid Card orders and existing refunded states were rejected by the fulfillment guard. | Enforce the unpaid guard on status/payment/method transitions and allow the existing refunded state. New unpaid fulfillment and all test-paid/test-fulfillment transitions remain blocked. |
| Medium | Query-only result navigation reused the previous order selector/poller and could show that order's status. | Key the result component by full route, disposing old polling and rejecting its late responses. Status requests now have a 10-second timeout. |
| Low | SDK timeout left a stale script and load listeners, obstructing a subsequent visit/retry. | Remove the failed/timed-out script and its listeners; a subsequent mount loads the pinned SDK afresh. |

1. **Money:** The actual checkout handler drops forged subtotal/discount/fee/shipping/tax/total/currency fields and rejects forged line prices. The existing transactional RPC reads locked catalog prices, revalidates coupons, uses numeric(12,2) arithmetic and applies the saved fee. Initiation accepts only an owned order reference/locale and converts the saved EGP total exactly to integer cents. Reconciliation checks that snapshot again under locks. Shipping remains calculated later; no tax or shipping calculator was introduced.
2. **HMAC:** Rechecked the current official [20-field transaction HMAC order and SHA-512 procedure](https://developers.paymob.com/paymob-docs/developers/webhook-callbacks-and-hmac/hmac/hmac-transaction-callback). POST `obj.id`, `order.id` and `source_data.*` are read from their correct locations; booleans become lowercase strings, values concatenate without separators, and comparison uses timingSafeEqual after exact hexadecimal-length validation. Missing/null/object fields, wrong secret, altered amount and malformed signatures reject. No order lookup/reconciliation precedes signature validation. Unsigned merchant references, extras and `is_live` are not authority.
3. **Database/RLS:** The edited migration remains unapplied remotely. No data rewrite/drop/delete or browser grant was added. FK restrictions, per-order/provider attempt uniqueness, unique intention/provider-order IDs, global provider/transaction uniqueness, indexes, constrained states and timestamps are appropriate. Both tables enable RLS without browser policies/grants. Owner-filtered APIs expose safe projections; security-definer RPCs fix search_path, verify the service role and deny browser execution. Historical preservation and the newly discovered edit/refund regression are tested. Tests apply migrations only to disposable PGlite/native PostgreSQL databases.
4. **Concurrency:** The old Promise.all claim test used one PGlite connection; it is now accurately named as repeated-claim coverage. New native PostgreSQL 17.9 checks use independent sessions and observed lock barriers. They prove one attempt from three waiting claims; one transaction for racing callbacks; unchanged serialized-unit allocations, movements and stock; no test-mode paid event/shipping job; one paid transition/shipping job in a dormant live fixture; rejection of a transaction ID racing between two orders; and callback observation of a committed cancellation. Native tests create/destroy their own local cluster and accept no database URL.
5. **State/retries:** Success is terminal. Failure can become success; stale pending cannot undo failure, and stale failure cannot undo success. Order/payment state remain separate. No callback recreates orders or allocates inventory. Cart UUID retries preserve one order/allocation. Uncertain initialization never sends another POST; safe error_code persists for manual provider reconciliation. Pending/failed unexpired intentions reuse one session, while expired/uncertain attempts require review. Abandonment keeps existing stock allocation until staff handling; automatic expiry/release/recovery remains outside this phase.
6. **Test/live guard:** Runtime defaults off, rejects live mode and mismatched key/integration modes; SQL claim/store also only permit test intentions. Signed integration/provider-order IDs bind the callback to the persisted mode; unsigned `is_live` cannot override it. Test success updates only the private ledger, clears the client secret and projects `test_succeeded`; the order stays unpaid. Order-update/packing guards separately prevent staff or browser paths from turning that test order into paid/fulfilled commerce. This is appropriate for the current foundation.
7. **Future isolated staging:** The provider ledger can exercise intention → Pixel → signed callback → test result now. Full commerce paid/fulfillment behavior is separately exercised with privileged, disposable dormant-live fixtures. Actual TEST callbacks intentionally cannot mark even a staging commerce order paid in this version. Before full staging commerce acceptance, a separately reviewed staging-only settlement policy must be restricted to an isolated database/environment; changing `mode`, copying test keys, deployment, or an ordinary toggle is not an override. No production bypass or new payment feature was introduced in this review.
8. **Pixel/privacy:** Rechecked official [Intention](https://developers.paymob.com/paymob-docs/developers/intention-apis/create-intention) and [Pixel](https://developers.paymob.com/paymob-docs/developers/checkout-experiences/pixel-embedded) documentation. The approved publicKey/clientSecret/elementId/card-method options and module-script/two-stylesheet loader match; version remains pinned to 1.2.8. Both saving flags remain false. ELcomputer creates no raw card inputs/state/API fields/storage or analytics/error payload. SDK completion payloads are discarded. No secret/HMAC key enters public runtime config, SSR, bundles or customer API projections. Actual third-party field/3DS/lifecycle behavior still needs merchant staging acceptance; the SDK exposes no documented destroy method.
9. **Result/manual methods:** Browser redirect/SDK success is never payment proof. The result reads the authenticated customer's own state, drops provider query fields, polls at three seconds for at most ten requests and disposes on navigation. EN/AR × mobile/desktop × light/dark plus System checks pass. Cash/manual fees, proof status and settings behavior are unchanged. Bank Transfer/InstaPay were already disabled: the parent commit's PROJECT_STATE.md records this before the Paymob commit, and the old payment-method migration defaults both false. The foundation contains no settings UPDATE or enablement-default change. PayPal remains out of scope.
10. **Errors/logging:** Timeout, connection failure, provider rejection, malformed responses, invalid callbacks, unknown orders and financial/context mismatches return safe errors without provider bodies, keys or customer/card payload. Initiation stores bounded normalized diagnostic codes, while callback HTTP status distinguishes invalid/conflicting/retryable conditions. There is no raw callback logging. A native fetch test confirms the same timeout also aborts a stalled response body after headers; no POST retry occurs. Merchant delivery/retry behavior and production proxy query-log retention still require configuration review.
11. **Tests added/changed:** Expanded missing/malformed/wrong-secret/uppercase HMAC coverage and historical-order coverage in paymob.test.mjs. New paymob-security.test.mjs executes actual handler/component setup code with infrastructure fixtures: normalized disabled gate, forged financial fields, streaming upload limits/timeouts, private runtime/Pixel config, SDK retry/payload-free callbacks, bounded result polling, navigation cleanup and stale responses. New paymob-concurrency.test.mjs covers genuine multiple-session races; resetDatabase helper shares real schema preparation with that disposable server. No application dependencies were added.
