### Verified existing systems and reuse

- **VERIFIED EXISTING:** Nuxt 4.4.8 uses `@nuxtjs/supabase` 2.0.9, Nitro `server/api` routes, Tailwind, default/account/dashboard layouts, and blue storefront/dashboard styling. Database types are disabled in `nuxt.config.ts`; there is no generated database type file or lint script. The repository has PGlite migration tests, Nuxt typecheck, and build scripts.
- **VERIFIED EXISTING:** Customers and staff share Supabase Auth identities. `customer_profiles` has name, email, phone, active flag, and ID linked to `auth.users`; `admin_users` has active state, owner/admin role, and JSON permissions. Server helpers `requireCustomerRequest` and `requireAdminRequest` verify bearer tokens and load these records. Existing support permissions are `support.view`, `support.reply`, and `support.manage`; the dashboard route guard is supplementary to server checks. Reuse these identities and permissions rather than create a new staff system.
- **VERIFIED EXISTING:** `customer_orders.user_id` identifies the customer; order items and shipping jobs supply context. The existing ticket system has private `support_tickets`, messages, attachments, audit events, service-only RPCs, and support/customer Nitro APIs. The Help Center has public article search and dashboard editing. The `support-attachments` bucket is private. Reuse its validation, service-client, download and authorization patterns, but keep chat transcript tables separate from ticket tables.
- **VERIFIED EXISTING:** `/account/messages` is order-team/packing communication, with limited customer replies; `/account/support` is asynchronous ticket work; `/dashboard/crm` also has separate CRM support activities. Live Chat belongs inside Customer Support navigation, with optional account chat history and a link from Help Center. It should not repurpose Messages or CRM records.
- **VERIFIED EXISTING:** Ticket and account unread indicators refresh on page load; no chat Realtime channels or Postgres Changes subscriptions are present. `useStorePresence` sends HTTP analytics presence and is unrelated to Supabase Realtime. Existing ticket APIs use service-role access after server authorization; private ticket tables have RLS and no browser-role grants. `site_settings` is publicly selectable in full, so confidential chat limits and controls must not be placed there without a separate public projection.
- **VERIFIED EXISTING / NOT VERIFIED:** `supabase/config.toml` disables anonymous Auth sign-ins. `handle_new_customer_profile` inserts `new.email` into a non-null profile field, so anonymous Auth creation would fail unless adjusted. The account middleware checks for a profile but does not reject a missing one. Local files and prior handoff show support migrations deployed to project `zsqhuwgoasrexdnamlks`; current remote settings, Realtime policy, live Storage behavior, and authenticated browser flows were not inspected in Phase 0.

### Proposed data and workflow

- **DATABASE CHANGE / PROPOSED:** `chat_settings`: one typed, validated singleton with enabled flag (default **off**), availability override, IANA timezone, weekly hours, welcome/offline text, guest contact rule, default 4-second send cooldown, body and attachment limits, assignment, transfer/reopen and ticket behavior. Admin changes use a server API and an audit event. A public status endpoint returns only display-safe fields. Proposed initial timezone is `Africa/Cairo`, subject to confirmation before staging.
- **DATABASE CHANGE / PROPOSED:** `chat_conversations`: UUID and human reference, either authenticated `customer_id` or anonymous `guest_auth_user_id`, captured guest name/contact, `waiting|active|closed` status, `live|offline` intake mode, assigned admin, optional owned order and linked ticket, last activity/message markers, timestamps, and revision. One non-closed conversation per actor is enforced atomically so refresh/two tabs resume instead of creating duplicates; old waiting conversations need explicit expiry/closure so they do not block new work indefinitely. Closed history stays closed until an authorized reopen.
- **DATABASE CHANGE / PROPOSED:** `chat_messages`: conversation FK, global increasing sequence, sender kind and verified actor ID, plain-text body, public/internal visibility, client idempotency UUID, timestamp, and uniqueness per actor/conversation/key. `chat_events` stores creation, identification, claim/assignment/transfer, staff reply reference, status, order link, ticket conversion, and closure with old/new actor and timestamps. Ephemeral typing/heartbeat events are excluded. `chat_read_state` stores a monotonic last-read public message sequence per customer/guest/staff participant. `chat_attachments` links a message to a private object path and validated metadata. Add indexes for queue/status/activity, customer/guest history, assignee, order, transcript cursor, and unread queries; use foreign keys and restrictive delete behavior to preserve history.
- **DATABASE CHANGE / PROPOSED:** A small `chat_agent_availability` lease records an authorized agent's declared online/away choice and short expiry; this is routing state, not permanent presence history. A bounded `chat_rate_limits` counter table supports atomic, shared IP/actor abuse limits; store keyed hashes instead of raw IP where possible. Extend the existing fail-closed system-reset allowlist and private-object manifest. A full reset may clear chat data; a content reset must not erase chat history.
- **PROPOSED:** Chat enabled + hours/override + at least one eligible agent with a valid lease determine live availability. Force-online bypasses hours but cannot claim a live agent exists when none does. Offline intake saves a waiting conversation and message, with a clear response expectation; optional ticket conversion is a separate action. Manual claim is the initial assignment mode. Staff with `support.reply` claim via one row-locked transaction; `support.manage` transfers/assigns. Only the current assignee replies. Revision/expected-state checks give one winner in competing claims and serialize send versus close. Every transition and reply is durable before clients are notified.
- **PROPOSED:** Customer unread counts include only newer public staff messages; staff unread counts include only newer customer messages. A read update can advance only to a message actually fetched/visible to that actor, using `greatest` to handle two tabs. Inbox attention uses waiting status and last customer/staff message markers. Internal notes are excluded from customer APIs, customer Realtime signals, and customer unread logic.
- **PROPOSED:** Text send is a server-authorized, transactional RPC: check actor/conversation/status/assignment, use the saved setting to enforce the 4-second default cooldown, validate length, apply shared abuse counters, insert once by idempotency key, update conversation markers, and emit a committed signal. Also limit messages/minute, conversation creations, repeated identical submissions, attachment attempts, and HTTP body size. The composer stays editable during cooldown. Server IP attribution must use trusted proxy configuration.

### Identity, Realtime, and security

- **SECURITY-SENSITIVE / PROPOSED:** Signed-in chat uses the verified customer JWT and active profile; the browser cannot submit a trusted `customer_id`. Guests provide name plus valid email or mobile; these contact values are unverified and grant no order/account access. The preferred guest transport uses a **separate** Supabase client/session with anonymous Auth, created only when a guest starts chat. It must not replace the site's normal login session. This requires a migration that skips customer-profile creation for anonymous Auth users, a review of all existing `authenticated` grants/RLS/API paths, and a project Auth setting change only after staging approval. Two verified sessions (guest and permanent customer) are required for a controlled guest-to-account link; typed contact matching alone never links. Once linked, guest channel/API access is revoked and the link is audited. Supabase's [anonymous-user documentation](https://supabase.com/docs/guides/auth/auth-anonymous) confirms these users receive the `authenticated` database role, making that audit mandatory.
- **SECURITY-SENSITIVE / PROPOSED:** New chat tables have RLS enabled and no direct anon/authenticated CRUD grants. Nitro APIs use the existing server-only service client after token and active-account/permission checks. Service-only RPCs perform atomic writes; revoke public/browser execute rights. `realtime.messages` policies permit **private** topic joins only for the linked customer/guest or active staff with `support.view`, using a narrow `security definer` membership helper with fixed topic parsing. Only the assignee may send staff replies through the API; `support.manage` controls transfers/closure. Customer projections exclude internal notes, staff metadata, and unrelated order data. Test RLS, direct RPC denial, IDOR, forged identity/order/conversation IDs, disabled accounts, and cross-guest access. Realtime authorization is evaluated at join/token refresh, so permission revocation must also be enforced on every API fetch and payloads must contain no sensitive bodies.
- **PROPOSED:** Supabase private Broadcast topics: one lightweight `chat:inbox` for authorized support staff; `chat:public:<conversation-id>` for the owning customer/guest and viewing staff; `chat:staff:<conversation-id>` for staff-only internal activity. Database-triggered `realtime.send` signals after committed changes carry IDs, sequence/revision and event kind only, never full bodies or customer contact. Clients fetch deltas through authorized APIs and reconcile on subscribe, reconnect, focus, and refresh. Typing uses heavily throttled, expiring ephemeral Broadcast through a rate-limited path; no keystrokes or typing rows in Postgres. Connect customers only after they open chat, retaining the active subscription while minimized; agents join the inbox while in the support workspace and only the conversation being viewed. Supabase [Broadcast guidance](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes) favors this over broad Postgres Changes for scale, while [private-channel authorization](https://supabase.com/docs/guides/realtime/authorization) requires topic RLS. Verify remote Realtime public-access setting and existing consumers before changing it.
- **PROPOSED:** A separate private `chat-attachments` bucket follows the existing authorized-download pattern. Allow initial JPEG/PNG/WebP/PDF only, with MIME, extension, signature, size/count, and server request-body checks; generated object paths; no public URLs; ownership and internal-note checks before download. Malware scanning is outside V1 unless an existing service is found. Message text renders escaped plain text; any links use a strict safe URL renderer. Transcript pagination uses `(created_at, id)` or the monotonic sequence; never load unbounded history.
- **PROPOSED:** Authenticated customers can choose only their owned orders. A guest cannot link an order based on a reference; linking follows verified account association. Agent context joins existing profile, order, shipment, ticket and previous-chat tables with scoped, batched queries. Chat-to-ticket creates an existing `support_tickets` record through a service-only conversion transaction, links the conversation and ticket once, carries customer/order when verified, saves an audit event, and references the chat transcript rather than copying it. Guest tickets can retain captured contact but do not gain account ownership without the verified linking flow.
- **PROPOSED quota impact:** No chat socket for untouched storefront visitors. Expect roughly one Realtime connection per opened customer chat or active support browser, one staff inbox topic, and one or two topics for the viewed conversation. Signals and throttled typing keep delivered events far below sending full transcripts to all staff. Actual project plan, concurrent users, peak joins, and message fan-out are **NOT VERIFIED**; measure them in staging against current [Realtime limits](https://supabase.com/docs/guides/realtime/limits).

## Help Center and customer support

The Help Center and support-ticket application is deployed to the `new-elcomputer` PM2 process at `new.elcomputer.net`. Both `20260919120000_help_center_support.sql` and `20260920120000_support_unread_replies.sql` have been applied to the linked Supabase project (`zsqhuwgoasrexdnamlks`).

### Architecture

- Public `/help` and `/help/[category]/[slug]` pages use server APIs backed by PostgreSQL full-text search. Categories are database-managed. Only active categories and published articles are returned publicly. Article bodies use the existing safe Markdown renderer.
- `/dashboard/help` manages categories and draft, published, or archived articles. `help.view` controls reading; `help.edit` controls changes. Archiving is the safe delete action.
- `/account/support` and `/account/support/[id]` let authenticated customers create, list, reply to, close, and recently reopen their own tickets. An order link is optional and verified against `customer_orders.user_id`.
- `/dashboard/support` and `/dashboard/support/[id]` let authorized staff search, filter, read, reply, add internal notes, change status/priority, and assign tickets. Existing `admin_users` and admin permissions are reused. Existing CRM support records are separate.
- Ticket assignment is limited to active staff with reply permission (or the owner), so a view-only account cannot become the assignee.
- The customer account navigation and ticket list show unread customer-visible staff replies. The admin ticket list shows a shared needs-attention count for new tickets and customer replies.
- Admin ticket details use existing `customer_orders.payment_status` and `shipping_order_jobs` data for payment and shipment context. No order values are copied into support tables.
- Customer and admin APIs are under `server/api/support`, `server/api/admin-support`, `server/api/help`, and `server/api/admin-help`. `server/utils/supportTickets.js` handles ownership, threads, uploads, and downloads; `server/utils/helpCenter.js` validates article/category input.
- `app/composables/useSupportClient.js` sends the signed-in user's access token. The Supabase service-role key stays in server runtime configuration and is never returned to the browser.

### Database and security

The local migration creates `help_categories`, `help_articles`, `support_tickets`, `support_ticket_messages`, `support_ticket_attachments`, and `support_ticket_events`, with foreign keys, constraints, indexes, and timestamp/history triggers. Ticket states are open, in progress, waiting for customer, waiting for support, resolved, and closed. Priority is staff-controlled. An event table records creation, status, priority, and assignment changes.

RLS is enabled on all six tables. Public roles can select only active help categories and published articles in active categories. They have no grants or policies for ticket tables. Ticket-write RPCs have execution revoked from public, anon, and authenticated roles; server APIs call them with service role only after verifying the bearer token and authorization. Customer APIs scope ticket and order reads by authenticated user ID. Customer responses exclude internal notes and attachments on those notes. Staff APIs require `support.view`, `support.reply`, or `support.manage` as appropriate. Attachment downloads check ticket ownership or active staff permission, and deny disabled customers. The `support-attachments` Storage bucket is private; application APIs use server-side download after authorization. File types are PDF, TXT, JPG, PNG, and WebP, with a 5 MiB file limit and signature checks. Multipart parsing still buffers the request; configure an appropriate reverse-proxy body limit before production.

The migration also updates the full-system-reset allowlist and captures existing private support object paths in the reset manifest. Full reset deletes support rows and then removes only captured support files. Content reset removes Help Center content while preserving tickets and their conversation. Both behaviors were tested in an isolated PGlite database.

The second migration adds `support_ticket_messages.customer_read_at`, an unread index, and service-role-only count functions. A customer can mark only visible staff replies on an owned ticket as read. Direct browser-role access to private messages and unread functions remains denied. Shared authentication helpers now log database diagnostics server-side and return a safe generic 500 response while retaining distinct 401/403 behavior.

### Notifications and future integration

V1 shows a support attention count to authorized staff when a customer creates or replies to a ticket. Customer-visible staff replies appear as unread in the customer account navigation and ticket list until the customer opens the conversation. Internal notes do not produce customer unread state. These indicators refresh on page load; there is no push, email, or polling. Ticket events and `last_reply_at` can support later delivery. Order linkage uses the existing website order ID, so a future ERP view can join through the existing order/ERP mapping rather than duplicating ERP data. Article helpfulness feedback and email notifications are Phase 2.

## Customer account redesign — deployed

The customer account redesign is deployed to `new.elcomputer.net`. A shared `account` layout provides account navigation for Overview, Orders, Messages, Support, Wallet, and Profile. Orders and Wallet are real routes rather than anchors on Overview. The storefront's order shortcuts lead to `/account/orders`.

Overview and Orders read the existing `customer_orders` and `customer_order_items` tables under the customer's Supabase RLS policies. Order detail uses a new authenticated, ownership-scoped read endpoint for order items and selected `shipping_order_jobs` fields. It returns 404 for an order not owned by the requester. The progress view shows only confirmed placement and current status; there is no status-event history from which to claim intermediate milestones or their dates. Messages remain order-team communications; Support remains the separate ticket system. A support link from an order preselects only an owned order. Wallet shows the existing `customer_profiles.wallet_balance` and does not invent transactions. Profile editing uses the existing customer-profile fields and RLS.

Available data: order status, order-item snapshots, payment status/paid time, shipping method/review status, PDC airway bill, and latest provider status/time. Missing data: delivery estimate, reliable delivered timestamp, customer refund-request stages, customer return workflow, and wallet transaction history. Staff inventory returns are not a customer refund-request system.
